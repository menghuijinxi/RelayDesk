# 文件和文件夹传输行为设计

本文档描述聊天消息中文件、文件夹附件的目标行为。它是后续实现前的行为约束，
不描述图片附件；图片继续按现有预览图、hash 存储和点击看原图逻辑处理。

## 目标

- 文件和文件夹作为聊天消息的一部分展示，但默认只发送传输邀约，不立即传输内容。
- 发送端和接收端都能在消息框内完成传输操作，不依赖独立传输页。
- 文件和文件夹最终落盘时尽量保持原名，不像图片那样按内容 hash 命名存储。
- 重名时接收端可以选择快速覆盖，也可以选择保留两份并自动追加序号。
- 发送失败、取消、拒绝和异常都必须在对应消息框内显示明确原因。
- “再次发送”必须支持断点续传，不能默认从头重传已经完整接收的内容。

## 非目标

- 不改变图片附件的 hash 存储规则。
- 不在本轮设计里确定文件、文件夹的长期归档规则；本文只定义聊天传输行为。
- 不要求接收端在收到邀约时自动写入最终目录。
- 不要求文件夹覆盖时删除接收端已有但发送端不存在的额外文件。

## 术语

- 传输邀约：聊天消息中的文件或文件夹元数据，包括名称、大小、类型、传输 ID。
- 主动发送：发送端主动请求开始传输内容。接收端仍可以拒绝或选择接收策略。
- 接收：接收端确认接收，并使用自动重命名策略保存。
- 覆盖：接收端确认接收，并覆盖同名目标。
- 再次发送：发送端在取消、拒绝、失败后重新发起同一个传输，优先断点续传。
- 完整接收：文件所有字节，或文件夹清单中的所有文件，都已接收并校验完成。

## 存储原则

文件和文件夹不进入图片 hash 存储体系。

发送端：

- 发送聊天消息时只记录源路径、原始名称、大小、类型和传输 ID。
- 默认不复制文件或文件夹到 outbox 缓存，传输时从源路径读取。
- 如果发送前源文件或源文件夹已经不存在，消息显示失败原因。

接收端：

- 文件默认保存为原文件名。
- 文件夹默认保存为原文件夹名，并保持内部相对路径结构。
- 如果目标名称已存在，点击“接收”使用自动重命名，点击“覆盖”使用原名称覆盖。
- 传输过程中的临时文件、断点信息、文件夹清单可以放入 `data/transfers/temp/`。
- 最终文件不按 hash 命名；允许保存校验值或分块状态作为传输元数据，但不能用它决定最终文件名。

## 重名处理

当接收端检测到最终目标已存在时，消息框显示：

- `接收`
- `覆盖`
- `拒绝`

点击 `接收`：

- 文件：`report.pdf` 已存在时，尝试 `report(1).pdf`、`report(2).pdf`，直到找到不存在的路径。
- 无扩展名文件：`README` 已存在时，尝试 `README(1)`、`README(2)`。
- 文件夹：`Project` 已存在时，尝试 `Project(1)`、`Project(2)`。

点击 `覆盖`：

- 文件：直接替换同名文件。
- 文件夹：使用同名文件夹作为目标根目录；传输清单中冲突的文件会被覆盖，
  接收端已有但不在本次清单中的文件保留。

如果没有重名，接收端只需要显示：

- `接收`
- `拒绝`

## 发送端消息框

### 文件

发送文件消息后，发送端消息框显示文件名、大小、状态文案和按钮：

- `主动发送`
- `取消`
- `打开`
- `打开文件夹`

成功完整发送后：

- 显示成功状态。
- 按钮变为 `打开`、`打开文件夹`。

取消、接收端拒绝或发送异常后：

- 在消息框中显示失败原因。
- 按钮变为 `再次发送`、`打开`、`打开文件夹`。

### 文件夹

发送文件夹消息后，发送端消息框显示文件夹名、文件数量、总大小、状态文案和按钮：

- `主动发送`
- `取消`
- `打开文件夹`

文件夹没有 `打开` 按钮。

成功完整发送后：

- 显示成功状态。
- 按钮变为 `打开文件夹`。

取消、接收端拒绝或发送异常后：

- 在消息框中显示失败原因。
- 按钮变为 `再次发送`、`打开文件夹`。

## 接收端消息框

### 文件

收到文件邀约后，接收端消息框显示文件名、大小和按钮：

- `接收`
- `拒绝`

如果存在同名目标，额外显示：

- `覆盖`

点击 `拒绝` 后：

- 消息显示 `文件接收已拒绝`。
- 不显示任何按钮。
- 发送端显示失败原因：`对方已拒绝接收`。

点击 `接收` 或 `覆盖` 且完整接收后：

- 按钮变为 `打开`、`打开文件夹`。

接收失败后：

- 消息框显示失败原因。
- 不显示任何按钮。

### 文件夹

收到文件夹邀约后，接收端消息框显示文件夹名、文件数量、总大小和按钮：

- `接收`
- `拒绝`

如果存在同名目标，额外显示：

- `覆盖`

点击 `拒绝` 后：

- 消息显示 `文件接收已拒绝`。
- 不显示任何按钮。
- 发送端显示失败原因：`对方已拒绝接收`。

点击 `接收` 或 `覆盖` 且完整接收后：

- 按钮变为 `打开文件夹`。

文件夹接收失败或未完整接收后：

- 消息框显示失败原因。
- 仍然显示 `打开文件夹`。
- 点击 `打开文件夹` 前提示未完整接收的文件数量，例如：
  `该文件夹还有 3 个文件未完整接收，是否仍然打开？`

## 传输进度展示

当前不保留右侧独立传输面板。所有传输进度、状态变化和失败原因都直接显示在聊天消息框内。

完整接收、失败、拒绝或取消后，不再保留右侧进度条模板或空状态文案。

## 状态模型

### 发送端状态

| 状态 | 说明 | 可见按钮 |
| --- | --- | --- |
| `Offered` | 聊天消息已发出，内容尚未开始传输 | `主动发送`、`取消`、打开类按钮 |
| `WaitingForPeer` | 已请求传输，等待接收端确认 | `取消`、打开类按钮 |
| `Transferring` | 正在发送内容 | `取消`、打开类按钮 |
| `Completed` | 接收端完整接收 | 打开类按钮 |
| `Cancelled` | 发送端取消 | `再次发送`、打开类按钮 |
| `Rejected` | 接收端拒绝 | `再次发送`、打开类按钮 |
| `Failed` | 传输异常结束 | `再次发送`、打开类按钮 |

打开类按钮含义：

- 文件：`打开`、`打开文件夹`。
- 文件夹：`打开文件夹`。

### 接收端状态

| 状态 | 说明 | 可见按钮 |
| --- | --- | --- |
| `Offered` | 收到传输邀约，尚未选择 | `接收`、`拒绝`，重名时还有 `覆盖` |
| `Receiving` | 正在接收内容 | 无按钮 |
| `Completed` | 完整接收 | 文件显示 `打开`、`打开文件夹`；文件夹显示 `打开文件夹` |
| `Rejected` | 接收端拒绝 | 无按钮 |
| `Failed` | 文件接收失败 | 无按钮 |
| `PartiallyCompleted` | 文件夹部分文件已落盘但未完整接收 | `打开文件夹` |

## 断点续传要求

`再次发送` 必须优先复用已有传输进度。

文件：

- 接收端记录已接收字节数和目标临时路径。
- 再次发送时，接收端返回当前已接收 offset。
- 发送端从 offset 继续发送。
- 完成时校验最终大小；如果协议提供校验值，也校验内容一致性。

文件夹：

- 发送端必须提供文件夹清单，包含每个文件的相对路径、大小和可选校验信息。
- 接收端按清单记录每个文件的状态：未开始、部分接收、已完成、失败。
- 再次发送时，接收端返回每个未完成文件的进度。
- 已完成文件不重复传输。
- 部分文件从已接收 offset 继续传输。

如果发送端源文件发生变化，导致大小或校验与原邀约不一致：

- 本次再次发送失败。
- 发送端显示原因：`源文件已变更，无法断点续传`。
- 后续如果需要支持“作为新文件重新发送”，应创建新的传输 ID。

## 失败原因

消息框必须显示用户能理解的失败原因，至少覆盖：

- 发送端取消。
- 接收端拒绝。
- 对方离线。
- 网络连接中断。
- 源文件或源文件夹不存在。
- 源文件读取失败。
- 接收端磁盘空间不足。
- 接收端没有写入权限。
- 文件大小不匹配。
- 文件夹清单不匹配。
- 路径不安全，例如文件夹清单包含 `..` 或绝对路径。
- 接收端目标被占用，无法覆盖。

## 协议扩展建议

当前传输协议只有 offer、chunk、complete，不能完整表达拒绝、接受策略、
取消、错误原因和断点续传。后续实现建议增加控制消息：

- `transfer_accept`：接收端接受传输，并携带保存策略 `unique` 或 `overwrite`。
- `transfer_reject`：接收端拒绝，携带原因 `user_rejected`。
- `transfer_cancel`：任一端取消，携带取消方和原因。
- `transfer_error`：任一端报告失败原因。
- `transfer_resume_request`：再次发送时询问接收端已有进度。
- `transfer_resume_state`：接收端返回文件 offset 或文件夹逐文件进度。
- `transfer_folder_manifest`：文件夹传输清单。

协议消息必须携带：

- `message_id`
- `part_id`
- `transfer_id`
- 发送设备 ID
- 接收设备 ID
- 附件类型：file 或 folder

## 历史记录字段建议

文件和文件夹消息部分需要能持久化以下信息：

- 原始名称。
- 原始大小。
- 文件数量，文件夹专用。
- 本地路径。
- 临时路径或断点元数据路径。
- 文件夹清单路径。
- 保存策略：未选择、自动重命名、覆盖。
- 传输状态。
- 失败原因。
- 已完成文件数量，文件夹专用。
- 未完整接收文件数量，文件夹专用。

失败原因要进入聊天历史，否则重启后消息框不能还原错误状态。

## UI 文案

按钮文案固定为：

- `主动发送`
- `取消`
- `再次发送`
- `打开`
- `打开文件夹`
- `接收`
- `拒绝`
- `覆盖`

状态文案建议：

- `等待发送`
- `等待对方接收`
- `正在发送`
- `正在接收`
- `已发送`
- `已接收`
- `发送已取消`
- `文件接收已拒绝`
- `发送失败：{原因}`
- `接收失败：{原因}`
- `文件夹未完整接收：还差 {count} 个文件`

## 实现顺序建议

1. 补齐历史记录和协议状态，不先改 UI。
2. 实现文件邀约、接收、拒绝、覆盖、自动重命名。
3. 实现文件断点续传和再次发送。
4. 实现文件夹清单、文件夹接收、部分完成状态。
5. 实现文件夹断点续传。
6. 最后补齐消息框按钮、失败原因展示和打开按钮行为。

## 待确认点

- `主动发送` 是否允许绕过接收端点击 `接收`。本文档当前假设不允许；
  接收端必须通过 `接收` 或 `覆盖` 确认保存策略。
- 文件夹 `覆盖` 当前定义为覆盖清单中的同名文件，不删除接收端额外文件。
  如果要做严格镜像覆盖，需要另加二次确认。
- 接收失败后文件不显示任何按钮；如果以后希望接收端也能主动重试，
  需要新增接收端 `再次接收` 行为。
