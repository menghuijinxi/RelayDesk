# 性能问题复盘

## 大文件传输导致聊天窗口卡顿

- 日期：2026-08-24
- 现象：传输大文件时窗口明显卡顿；传输未结束时切换到其他聊天再切回，真实传输仍在继续，但 UI 显示为中断或重试。
- 影响范围：SkiaUI 聊天窗口、传输进度显示、会话切换后的历史消息恢复逻辑。
- 根因：传输进度按 1 MB 分片更新，UI 签名使用原始已传输字节数，导致每个分片都触发聊天内容重建；第一次修复后虽然改为百分比，但百分比变化仍会替换整个聊天区，长聊天和大文件传输下仍会卡顿；同时历史消息加载时会把 `Transferring` 状态统一恢复成 `Interrupted`，没有判断当前进程内该传输是否仍然活跃。
- 排查路径：先确认传输线程实际未断，再检查会话加载时的状态恢复逻辑；随后检查 UI 签名生成路径，确认 `GetTransferredSize()` 和百分比变化都会放大全量刷新；最后检查传输卡片 DOM，确认原实现缺少可局部更新的进度控件 id。
- 最终解决方案：历史恢复时跳过当前进程内仍活跃的传输；待处理传输进度按 transfer/message/part 合并，只保留最新值且合并时不重复请求刷新；聊天 UI 签名不再包含纯进度，传输卡片增加稳定 id，纯进度变化只局部更新百分比文本和 progress value，状态变化仍全量刷新以更新按钮和状态文案。
- 验证方式：新增回归测试覆盖“活跃传输切换会话后仍保持传输中”和“待处理进度合并保留最新值”；运行 `relaydesk_app_runtime_update_prompt_tests` 通过，并重新编译 `relaydesk_skiaui`。
- 可复用经验：进度类高频状态不要进入 UI 全量 diff 签名，即使只按百分比变化也可能过重；应给高频变化区域提供稳定 id 并做局部 DOM 更新。从持久化历史恢复运行中状态时，必须先区分“上次进程遗留状态”和“当前进程仍活跃状态”。
- 快速检查清单：检查进度更新频率、UI diff 签名粒度、当前会话外进度队列是否合并、纯进度变化是否局部更新、历史恢复是否查询运行中任务或内存中的传输表。

## 切换聊天窗口触发重复全局布局

- 日期：2026-09-22
- 现象：聊天记录较多时切换联系人会卡顿约半秒，性能轨迹中 `recompute_layout_total` 累计耗时最高。
- 影响范围：联系人切换、聊天区重建、编辑器布局和设置界面刷新。
- 根因：一次界面刷新连续调用多个 SkiaUI setter，每次调用都立即执行样式重算和 Yoga 全局布局；联系人点击后的即时刷新没有同步 UI 签名，100 毫秒定时器还会重复刷新一次。图片解码是异步路径，不是这次累计布局耗时的主要来源。
- 排查路径：使用 `SKIATEST_PERF_CSV` 采集联系人切换测试，统计 `recompute_layout_total`、`style_recompute` 和 `layout` 的次数与耗时；随后分别验证批量更新和定时器去重对布局次数的影响。
- 最终解决方案：使用 SkiaUI 的 `beginUpdate()` / `endUpdate()` 把设备列表、聊天内容、编辑器和设置界面的成组修改合并为一次布局；联系人点击完成后立即更新 UI 签名，避免定时器重复刷新；SkiaUI setter 对完全相同的值直接返回，不再把布局标记为脏。
- 验证方式：同一联系人切换测试中，`recompute_layout_total` 从 122 次、2773.46 ms 降至 7 次、80.68 ms；其中前 6 次为页面初始化，联系人切换只触发 1 次布局。RelayDesk 除一个已确认与本次修改无关的既有剪贴板测试外，其余 38 项测试通过；SkiaUI 交互和键盘测试通过。
- 可复用经验：批量修改 UI 时必须建立事务边界，避免每个 setter 独立布局；即时刷新和定时刷新同时存在时，必须在即时刷新后同步用于去重的签名；性能判断应以布局调用次数和累计耗时为依据，不应仅凭单次布局耗时推断图片加载阻塞。
- 快速检查清单：检查一次用户操作调用了多少 setter、是否包裹批量更新、定时器是否重复处理同一状态、相同值是否仍标脏、读取滚动尺寸前批量更新是否已经结束。
