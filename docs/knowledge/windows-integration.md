# Windows 集成问题

## 开机自启状态必须同时读取 Run 和 StartupApproved

### 现象

用户在 Windows 10/11 的“启动应用”中禁用 RelayDesk 后，程序设置页仍显示“已启用”；程序再次
启动时还可能重新写入启动项。程序内重新开启开机自启，也可能因为系统禁用记录仍在而不生效。

### 影响范围

所有通过当前用户注册表 `Run` 值实现开机自启的 RelayDesk 版本，包括旧版界面和 SkiaUI 界面。

### 根因

Windows 的启动应用开关不会一定删除
`HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 中的值，而是把审批状态写入
`HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\StartupApproved\Run`。
只读取配置文件或 `Run` 值，无法判断系统是否已禁用该启动项。

### 排查路径

1. 对照 `config.json` 中的 `launch_at_startup` 与 `Run\RelayDesk`。
2. 检查 `StartupApproved\Run\RelayDesk` 的二进制数据。
3. 核对 `Run` 命令中的可执行文件是否为当前版本，注意引号、大小写、斜杠和附加参数。
4. 检查程序启动流程是否在读取系统状态前按旧配置强制重写启动项。

### 解决方案

- 同时读取 `Run` 和 `StartupApproved`，区分已启用、被系统禁用、未注册和指向其他程序四种状态。
- `StartupApproved` 首字节为 `0x02` 时视为启用，缺失时沿用 `Run` 状态；`0x03` 及未知数据保守地
  视为系统禁用。
- 应用启动时尊重系统禁用并同步配置；启动项指向旧版本时，按已保存设置迁移或清理。
- 用户重新开启时写入当前程序路径并删除禁用记录，然后重新读取注册表验证。
- 用户关闭时同时删除 `Run` 值和对应的 `StartupApproved` 残留。

### 验证方式

状态单元测试覆盖正确路径、系统禁用、缺失、旧程序路径、命令参数、路径大小写与未知审批数据；
两个界面目标均完成 MSVC Release 构建，并运行全量 CTest。

### 可复用经验

Windows 设置界面展示的状态可能由额外的审批注册表维护。实现系统集成功能时，不能把应用自己的
配置文件当作真实状态来源；写入后也应重新读取系统状态，避免界面显示未生效的设置。

### 快速检查清单

- `Run` 值是否存在并指向当前可执行文件。
- `StartupApproved` 是否存在禁用记录。
- 重新开启是否清除了禁用记录并完成回读验证。
- 外部禁用后，应用启动是否保持禁用。
- 旧版本路径能否按配置迁移或清理。
- 设置页每次打开时是否重新读取系统状态。

## 更新助手入口与重启进程的显示策略必须成对验证

### 现象

SkiaUI 版本收到更新后会退出，下载的程序文件也会替换成功，但新版本不会自动显示。单独观察文件替换结果，会误以为更新流程只在最后一步偶发失败。

### 影响范围

使用“立即重启”安装模式的 Windows 版本。旧版 EUI 和 SkiaUI 共用更新执行逻辑，但两个程序拥有不同的入口函数，因此入口遗漏只会影响其中一个界面版本。

### 根因

更新助手是从当前程序复制出的同一个可执行文件，它依靠 `--relaydesk-apply-update` 参数切换到更新执行模式。EUI 入口解析了该参数，SkiaUI 的 `wWinMain()` 却直接进入普通界面，因此 SkiaUI 复制出的助手会启动聊天窗口而不执行替换。与此同时，共用的进程启动函数固定使用 `SW_HIDE` 和 `CREATE_NO_WINDOW`，导致替换后的正式程序也按隐藏助手的策略启动。

### 排查路径

1. 在隔离目录复制目标文件和更新负载，直接以更新参数运行正式可执行文件。
2. 检查 `apply-update.log` 是否出现“helper started”“copy succeeded”和“restart requested”。
3. 如果没有生成日志，先检查所有正式程序入口是否在单实例检查和 UI 初始化前处理更新参数。
4. 如果日志显示重启成功但看不到窗口，检查 `CreateProcessW()` 的 `STARTUPINFO` 和创建标志。
5. 确认目标进程退出等待已完成，排除单实例互斥量仍被旧进程持有。

### 解决方案

- EUI 与 SkiaUI 入口都必须在进入正常应用流程前解析更新参数；参数以更新模式开头但格式无效时直接返回错误。
- 使用强类型显示策略区分进程用途：更新助手隐藏启动，替换后的正式程序使用 `SW_SHOWNORMAL` 启动且不设置 `CREATE_NO_WINDOW`。
- 回归测试必须使用真正的 SkiaUI 可执行文件作为助手，不能只调用共用更新函数，否则无法发现入口遗漏。

### 验证方式

可执行文件级测试让 SkiaUI 助手替换隔离目录中的测试程序，随后验证目标内容、更新日志、重启探针和 `SW_SHOWNORMAL` 启动状态。修复前测试在助手入口处超时；只补入口而未修正显示策略时，测试会在隐藏窗口断言处失败。

### 可复用经验

当程序通过“复制自身并传入特殊参数”实现助手进程时，每一个正式入口都属于该协议的一部分。共用业务函数的单元测试不能代替真实可执行文件测试。进程启动封装也不应把“后台助手”和“面向用户的正式程序”合并成一个默认隐藏策略。

### 快速检查清单

- 所有正式入口是否都在 UI、单实例和后台逻辑之前处理助手参数。
- 无效的助手参数是否会明确失败，而不是退回普通应用模式。
- 助手进程是否隐藏启动。
- 更新后的正式进程是否使用正常显示策略。
- 更新日志是否完整覆盖等待退出、复制和重启三个阶段。
- 回归测试是否经过真实可执行文件入口，而不只是直接调用内部函数。
